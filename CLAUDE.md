# LoomRoom

First-person 3D RPG. Unity 6000.5, URP, Cinemachine 3, Input System, Odin Inspector, Pixel Crushers Dialogue System, Synty art. Two controllable players: the **Room player** (exploration, never fights) and the **Table player** (first-person arms, melee combat). Rewritten in September 2026 on the conventions used in LoomyDungeons.

## Tooling

- **Use the Unity CLI (`unity-cli` skill) for all editor, scene, prefab and asset work. Never use Unity MCP servers (coplay-mcp, UnityMCP), not even to check editor state.**

## Settled decisions

- **Single `Assembly-CSharp`, no namespaces.** Same rule as LoomyDungeons. Do not propose asmdefs or namespaces.
- **One data asset per thing.** `CharacterData` holds what every character shares (identity, faction, stats, voice, animation triggers) and is used as-is by NPCs; `PlayerData : CharacterData` adds movement, stamina and starting items; `EnemyData : CharacterData` adds behaviour and attacks. Shared systems (health, damage, death) take `CharacterData`; player code reads `Player.PlayerData`, enemy AI reads `EnemyBrain.Data`. `ItemData` per item. A level's run is a list of `DungeonBiome` stages (look, enemies, loot profile, guardian); everyday loot is a `DungeonLootProfile` that picks catalog items by `ItemData.tier`, and hand-listed `DungeonLootTable`s are for special cases. Both are `LootSource`. `EnemyBehaviourProfile` only when several enemies must share tuning; otherwise behaviour lives on the enemy's own data. Everything lives under `Assets/Game/<Area>/`: all characters under `Characters/`, items in `Items/Data/{Weapons,Armor,Shields,Consumables,Trinkets}` (retired ones in `_Archive`), spells in `Combat/Spells/<Spell>`, custom effect assets in `Items/Effects`, audio data in `Audio/Data`, level assets in `Levels/`.
- **A character is one prefab file.** Its data (`PlayerData`, `EnemyData` or `CharacterData`) is stored inside the prefab as a sub-asset and edited on its Character component. Enemies are variants of `Characters/Enemies/Base/{Enemy base, Humanoid enemy base}`, NPCs of `Characters/NPCs/Base/HumanoidNPC`; shared changes go on the base. Create them with `Tools > LoomRoom > New Enemy` / `New NPC`; never put per-character data on managers. Layout: `Characters/{Scripts, Animations, Players/{Room,Table,Scripts,Input,Settings}, Enemies/{Base,Crypt,Town}, NPCs/{Base,…}}`. Hit feel (knockback via `EnemyFX`, bone recoil via `HitReactionController`, the single hit flash in `CharacterFX`) lives on the enemy bases.
- **Generic effects + custom escape hatch.** `EffectEntry` is one serializable class with an enum `type` and Odin `[ShowIf]` per field; `Custom` routes to an `ItemEffect : ScriptableObject` (scripts in `Items/Scripts/Effects`). `InteractionEffect` / `InteractionAction` mirror this for interactables. Add new effect types by appending to the enum, adding a case in `ItemEffectProcessor.Apply`, and a `Describe` line.
- **Enums are serialized by integer.** Explicit values, append only, retired numbers stay retired (see `StatType`, `ItemType`, `EnemyState`).
- **Singletons never auto-create.** `Singleton<T>` returns null and logs if the manager is missing. Managers sit under the `Systems` object in the scene; most are prefab instances (`Assets/Game/Core/Prefabs` and elsewhere); `WorldManager`, `PlayerManager` and the Lighting Manager are plain scene objects. Use `X.HasInstance` for cheap null-safe reads. Outside Play mode both `Instance` and `HasInstance` find the manager in the open scene (no log), so editor tools can use them.
- **Config lives on managers, containers live on players.** `InventoryManager` holds pickup and drop rules; `Inventory` (bag + hotbar, two components with different roles) and `Equipment` sit on each player so each keeps their own items and hands. Hand items stay in the hotbar while held; worn items (armour, pants, trinkets) leave the bag while equipped and return on unequip.
- **One owner per concern.** `InputManager` owns the input asset (maps: `Room`, `Table`, `UI`, `Dev`); `GameManager` owns the game-state stack (`Explore`, `Menu`, `Dialogue`, `Cutscene`, `Dead`, `Inventory`) and therefore the cursor, which input map is live, and HUD visibility. Nothing else touches `Cursor` or enables action maps. States are reference-counted: every `Push` needs exactly one matching `Pop` from the same owner (`Dead` is a plain flag).
- **Every hit is a `DamageInfo`.** Built by `Hitbox`, `EnemyBrain` or an effect; consumed by `CharacterStats.TakeDamage`; broadcast through `Character.Damaged` so FX, hit reactions, knockback and item triggers all see the same facts. `FactionRules.IsHostile` decides who can hurt whom.
- **Animator state is read by tag, never by name or layer index.** Arms windup/hold states are tagged `Attack`; the release states are `AttackRelease`, `AttackReleaseAlt` and `AttackHeavyRelease` (all four count as attacking). Arm block states are `Block` (only the LeftArm/RightArm layers; the FullBodyLayer state named "Block" is deliberately untagged). Enemy attack states are tagged `Attack`.
- **UI is authored in the scene.** Slots, the context menu, the drag ghost, notifications and vitals are scene objects; code only binds and fills them. Grandfathered: `ContextMenuUI` clones its authored button template.
- **Plain C# events.** UnityEvents only where a designer wires them (`InteractableTrigger.onInteract`, `CutsceneController.onStarted/onFinished`).
- **Save/load: `AdventureSave`** writes `loomroom-adventure.json` (a checkpoint at each floor, memorials, progression flags), atomically with a `.bak`. Items are saved by `ItemData.saveId`; never change one after release. Bump `AdventureSave.Data.Current` when the checkpoint shape changes (older checkpoints are then dropped, memorials and flags kept). `ItemStack`, `Inventory.slots`, `Equipment` and `ProgressionManager` flags stay plain (key, value) shapes; do not add non-serializable runtime state to them.

## Where things are

All game code lives in `Assets/Game/<Area>/Scripts` (paths below are relative to `Assets/Game`). The only scene is `Scenes/Room.unity`.

| Concern | Files |
|---|---|
| Game state, input, players, world | `Core/Scripts/{GameManager,InputManager,PlayerManager,ProgressionManager,WorldManager,Singleton}.cs` |
| Screen effects and fades | `Core/Scripts/{ScreenManager,ScreenEffectSettings}.cs`, shader `Rendering/RetroScreen.shader` (full-screen pass on `Rendering/Desktop Renderer.asset`) |
| Pixelator (3D pixel-art look) | `WorldManager` > Pixelator: on/off, camera mode (Default, Clean, Low Res), and toggles for Architecture, Props and Characters; Play mode only, flips live. `Core/Scripts/{PixelLook,PixelLookLibrary}.cs` swap each renderer between its original material and a `LoomRoom/Pixel Lit` copy (`Rendering/PixelLook/PixelLit.shader`: point-sampled colour, light evaluated per texel and stepped into bands, tiling patterns from `Rendering/PixelLook/Patterns`). Originals are never edited. `Tools > LoomRoom > Pixel Look > Build Materials` creates copies for new materials (keeps tuning); the library asset holds the pairs, their category, texel scales and each camera mode's effects. Low Res sets URP render scale and point upscaling through `ScreenManager` and restores them afterwards. Per-object pixelation (Object Pixel Size, Low-res Characters/Props) swaps to runtime twins on `Hidden/LoomRoom/Pixel Lit Object` (colour pass tagged `LoomPixelObject`), which `Core/Scripts/PixelObjectFeature.cs` (on the Desktop Renderer) draws at 1/N resolution and composites back with depth; transparent originals become a screen-door dither (`_DitherAlpha`). `PixelLit.shader` and `PixelLitObject.shader` share `PixelLitForward.hlsl` and must keep identical properties |
| Lighting and moods | `World/LightingManager.cs` + `LightingManager.Moods.cs`, presets are `SceneMood` assets (`Core/Scripts/SceneMood.cs`) |
| Character layer | `Characters/Scripts/{Character,CharacterStats,CharacterData,PlayerData,EnemyData,CreatureAudio,Faction,StatType,StatModifier,CharacterFX}.cs`, `Characters/Scripts/Editor/NewCharacterWindow.cs` |
| Enemy / NPC AI | `Characters/Scripts/AI/{EnemyBrain,EnemyAttackRunner,Perception,EnemyMotor,EnemyAttack,EnemyArchery,EnemyBehaviourProfile,NpcBrain,NoiseEvents}.cs`. `EnemyData.archer` makes any enemy an archer: the bow shot joins its attacks, the bow sits in the left hand (`EnemyWeaponLoadout`, grips in `Characters/Resources`), and the release clip's `OnAttackHit` looses a `Combat/Arrows/Arrow` (`ArrowProjectile`) |
| Player | `Characters/Players/Scripts/{Player,PlayerMotor,PlayerLook,PlayerFootsteps,PlayerCombat,PlayerCameraRig,PlayerAnimation,PlayerSettings}.cs`, MFPC modules in `Characters/Players/Scripts/Modules`. `PlayerInput.cs` is generated from `Characters/Players/Input/PlayerInput.inputactions`; never hand-edit it |
| Combat | `Combat/Scripts/{CombatManager,Hitbox,WeaponAnimationRelay,IDamageable}.cs` |
| Spells | `Combat/Scripts/{PlayerSpellcasting,SpellDefinition,SpellProjectile,SpellVisual}.cs`. One folder per spell in `Combat/Spells/<Spell>/` (data, hotbar item, hand/impact effects, sounds); projectiles are variants of `Combat/Spells/_Base/Base Projectile` that only add art. Arm clips in `Characters/Animations/Spells`, layer "Left Hand Spell" (tags `SpellEquip`, `SpellCharge`, `SpellRelease`) |
| Classes, level, skills, save | `Progression/Scripts/{AdventurerProgress,AdventurerClass,AdventureSkillData,AdventureRules,AdventureSave,AdventureMemorial,AdventureRoomPuzzle}.cs`, data in `Progression/Data`. Barony-style skills: 0-100, +1 by chance per successful action (`AdventurerProgress.Practise`) |
| Items | `Items/Scripts/{ItemData,ItemEnums,EffectEntry,ItemEffect,ItemEffectProcessor,EffectDispatcher,ItemStack,Inventory,Equipment,InventoryManager,WorldItem}.cs`, `Items/Scripts/Editor/ItemDatabaseWindow.cs` (`Tools > LoomRoom > Item Database`; `Tools > LoomRoom > Sync Item Catalog` refreshes InventoryManager's catalog) |
| Interactions, dialogue | `Interactions/Scripts/*` (incl. `HingedDoor`, `RoomLoopPortal`), `Dialogue/Scripts/DialogueBridge.cs` (Lua: `GiveItem`, `HasItem`, `SetFlag`, `GetFlag`, `DMSay`). `DungeonMaster` (on the Dialogue Manager) types a line at the top of the screen: `DungeonMaster.Say(text, clip/AudioData, mumble)` or a `DMLine` asset |
| Cutscenes | `Cinematics/Scripts/{CutsceneController,WakeUpCutsceneController,DinnerCutsceneController,TableIntroController,TableManager}.cs` |
| Table levels (town, dungeons) | `Levels/Shared/Scripts/*` (`TableLevelLoader`, `TableLevelReveal`, `DungeonGenerator` + `DungeonGenerator.Growth`, `DungeonLayout` + `DungeonLayout.Grown`, shapes in `DungeonShape`/`DungeonRoomShape`, furnishing in `DungeonPropRule`...), catalog `Levels/Resources/TableLevels.asset`. The level's `startingRoom` is a room template prefab (Dungeon1: `Rooms/Templates/Starting room`) used as room 0 on floor 1 and on the first floor of each new biome; the player spawns at its centre facing its one door, which always gets the level's door prefab. A `DungeonRoomTemplate` can hold a whole room: painted footprint (`DungeonShapeGrid`, shared with `DungeonRoomShape`), style, height in tiles, `WallLight` sockets; in Prefab Mode it shows an unsaved preview of floor, walls and socket lights |
| UI | `UI/Scripts/*`. `AnnouncementUI.Show(title, sub)` is the centre-screen line (level ups and new skill tiers). UI sounds, including skillUp, levelUp, shopTrade and the dmMumble1..6 syllables, are keys in AudioManager's UI Library. UI colours live on `UIManager` (Theme: shadow, panel, panel shading, frame, frame highlight, text, dim text; Status: health, mana, stamina, experience, gold, boss health, recent damage). Opt-in only: kit art follows the Theme through the `Kit Palette` material (a UI that should differ gets a copy of that material), other graphics follow a slot with a `UIColor` component. Kit sprites are greyscale value maps (black shadow, dark grey panel, light grey to white frame to highlight). Menus use the pixel kit in `UI/Sprites/Kit` (sliced at 1/3 pixels-per-unit multiplier) and the TMP fonts `PIXEARG_ SDF` (titles) and `PixelOperator` (body). Table menu: `UI/Prefabs/Adventure/{Table adventures,Adventure Card}` |
| Runs, log, currency, pooling, settings | `Game/Core/Scripts/{RunManager,MessageLog,PoolManager,UserSettings}.cs`, `Game/Items/Scripts/Currency/*` (CurrencyManager config, Wallet on the player), UI in `Game/UI/Scripts/{MessageLogUI,GoldCounterUI,BossBarUI,RunRecapUI,PauseMenuUI,SettingsUI,ShopUI}.cs` |
| Dungeon biomes, bosses, templates, features | `Levels/Shared/Scripts/{DungeonBiome,DungeonBossEncounter,DungeonRoomTemplate,DungeonSocket,DungeonDestructible,DungeonCorpse,Merchant,DungeonAmbience}.cs`, `Features/*`; guide in `Docs/Dungeon-features.md` |
| Dungeon lighting | Barony-style dark on every dungeon floor, whatever the preset: `LightingManager`'s Dungeon darkness settings cap ambient light (`darkAmbient`, default matches the Darkness preset) and the sun, with optional black distance fog; dungeon moods carry `MoodState.darkness` (set in `TableLevelData.DungeonLighting`), and a biome can opt out with `litThroughout`. Each biome picks its lighting preset for colour (Look tab), wall lights placed by `DungeonGenerator.PlaceTorches` from the biome's `lightingPrefabs` (`DungeonWallLight`: prefab, weight, optional colour), falling back to the level's list (Dungeon1 uses `Levels/Dungeon1/Prefabs/Props/Wall torch`, `TorchFlicker`). Room templates place their own with `WallLight` sockets; colour priority is socket, room template, room profile, list entry, and the player's lights in `Characters/Players/Scripts/FirstPersonLighting.cs`: a world light high above the head, a ceiling light below the floor (rendering layer "Ceiling"), and a soft fill for arms and held items (rendering layer "First Person"). URP reads light layers from `UniversalAdditionalLightData`; use `FirstPersonLighting.SetLayers` |
| On-screen text | `DungeonMaster` (on the Dialogue Manager) is the Barony-style feed in the lower middle: `MessageLog` events in white, kills orange, DM lines in their own colour; Combat lines stay in the history only. `ExperienceBarUI` is the top XP bar with the "X increased!" skill popup |
| Table player arms animation | `Characters/Animations/FirstPersonTable.controller`, clips in `Characters/Animations/FirstPersonPlayer` (all hand-authored) |

## Known leftovers

- The wake-up timeline's animation track is empty; `WakeUpCutsceneController` only fades and plays music over it.
- Every clip the third-person controllers use lives in `Characters/Animations/ThirdPerson/{Locomotion,Combat,Gestures,Sitting,Player}` (the StarterAssets FBX clips were moved to `Player`). `HumanoidController` locomotion is a 2D blend on `MoveX`/`MoveZ` (local velocity, set by `EnemyMotor`). `Assets/ThirdParty/StarterAssets` scripts are unused.
